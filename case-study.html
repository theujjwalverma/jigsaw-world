THE ORIGIN STORY

1. The Vision: Frictionless Fun for Team Sessions

The project was born out of a simple need: creating an engaging, competitive multiplayer game for company team-building sessions and fun Friday competitions.

Most corporate multiplayer games are plagued with onboarding friction—mandatory sign-ups, corporate SSO restrictions, app downloads, or complex lobby setups. We wanted an experience where anyone on a laptop or smartphone could open a 6-digit room code, click their name from the player list, and immediately dive into the deeply satisfying, tactile joy of interlocking jigsaw pieces snapping together with real-time leaderboard rivalry.

INCIDENT ROOT CAUSE ANALYSIS

3. The Stress Test: 40 Players & Immediate Cascading Failure

Failure Analysis

During our first large-scale tournament test, 40 participants entered the room and clicked Start Round 1 at the same moment. Within 30 seconds, the entire infrastructure froze into a dead lock and crashed. Here is the post-mortem of the 5 fatal failure points:

1

The Base64 Memory Bomb

High-resolution round images were stored as multi-megabyte Base64 strings. Because every player had a copy of the round config, the server repeatedly duplicated these gigantic strings in Node's heap memory for every single connected client.

2

Aggressive 2-Second REST Polling Storm

All 40 client browsers were querying the server every 2,000ms requesting the entire tournament state JSON snapshot. This generated over 100 MB/second of serialization and JSON streaming over HTTP.

3

Synchronous SQLite Disk Locks on Every Move

Every single piece drag, drop, or return was sent to the server, triggering a synchronous SQLite file write of the whole tournament JSON on Node's single-threaded event loop, blocking all other requests.

4

O(N²) WebSocket Broadcast Storm

Every minor piece coordinate shift by one player was broadcast over WebSockets to all 39 other players—flooding the server with 800+ messages/second of completely useless visual noise.

5

Out-Of-Memory (OOM) Crash on 512MB Container

On a 512MB RAM container (such as Render's free tier), the Node.js memory limit was blown out immediately. WebSockets timed out, triggering a mass reconnection avalanche that kept the server dead.

THE ARCHITECTURAL PIVOT

4. The Solution: Local-First + Serverless Reactive Cloud

Now in Production

We solved the crisis by reimagining the game from the ground up using the Local-First Principle. Instead of forcing the server to babysit every single puzzle move, we delegated full execution power to the browser, reserving the cloud strictly for what matters: final scores and the live leaderboard.

1

100% Client-Side Puzzle Execution (0 Network Overhead)

Every piece drag, snap, placement, and move count is computed locally in the player's browser memory via C.movePiece() in 0.05ms and saved to localStorage. While players are actively assembling puzzles, network traffic is literally 0 KB/s.

2

Static CDN Asset Delivery (Zero Database Footprint)

Images are completely divorced from the database. Puzzles are served as static files via Vercel / GitHub's multi-gigabit Global Edge CDN. Browsers cache the images once; no Base64 strings ever touch the state or network.

3

Reactive Push via Convex Cloud (No Polling)

Replaced aggressive 2-second polling with Convex Cloud's reactive WebSocket subscriptions. When a player finishes a round, a tiny 150-byte score payload is submitted. The cloud pushes fresh standings only when a rank change actually occurs.

4

Elimination of the Server Bottleneck

No 512MB container exists to run out of memory. Static assets are delivered by edge servers, while Convex Cloud handles automated horizontal scaling, connection pooling, and sub-millisecond document indexing.

🌟 The Core Takeaway for Real-Time Event Apps

Never make the server compute what the user's phone or laptop can compute for free. By making gameplay local-first and keeping the cloud strictly for authoritative scoring and leaderboard distribution, you eliminate 99.9% of network overhead and make your system impossible to crash.
